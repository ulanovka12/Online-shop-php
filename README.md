# Online Shop — отчёт по проверке бизнес-логики

Учебный интернет-магазин на чистом PHP (без фреймворков, свой роутер/автозагрузчик,
PostgreSQL через PDO). Ниже — отчёт о проверке бизнес-логики на баги и внесённых
исправлениях.

## Архитектура (кратко)

- **Core** — `Core\App`: самописный роутер (маршруты + диспетчеризация запроса).
- **Controller** — обработка запросов, у всех общий `BaseController` с сервисом авторизации.
- **Request** — обёртки над `$_POST`/`$_GET` со своей валидацией входных данных.
- **DTO** — простые неизменяемые объекты для передачи данных в сервисы.
- **Service** — бизнес-логика (корзина, заказы, авторизация).
- **Model** — доступ к PostgreSQL через PDO, ручная гидрация объектов.
- **Views** — PHP-шаблоны, подключаются напрямую из контроллеров.

## Отчёт по найденным и исправленным багам

### 1. SQL-инъекция и обращение к несуществующей переменной — `Model/User.php`
**Метод:** `getByIdProfile()`
**Было:** `id` подставлялся прямо в текст SQL-запроса (`... WHERE id = $userId`), плюс код
читал переменную `$result['image_url']`, которой в методе вообще не существует (аватар
профиля всегда оставался пустым).
**Стало:** запрос переведён на `prepare()`/`execute()` с именованным параметром `:id`;
опечатка исправлена на `$user['image_url']`.
**Почему это баг:** прямая подстановка значения в SQL-строку — уязвимость (SQL-инъекция),
а обращение к несуществующей переменной — просто ошибка (выдало бы Warning и пустой
результат).

### 2. Перевёрнутая проверка авторизации — `Controller/CartController.php`
**Методы:** `updateCart()`, `removeFromCart()`
**Было:** `if ($this->authService->check()) { header('Location: /login'); ... }` — но
`check()` возвращает `true`, если пользователь уже вошёл в систему. То есть на страницу
логина отправлялся именно залогиненный пользователь, а гость (для которого `check()`
возвращает `false`) пропускался дальше — и падал с ошибкой на `$user->getId()`.
**Стало:** условие исправлено на `if (!$this->authService->check())`.
**Почему это баг:** `check()` = "пользователь вошёл?", значит на логин нужно отправлять
тех, у кого ответ `false`, а не `true`.

### 3. `removeFromCart()` не мог получить ID товара — `Controller/CartController.php`
**Было:** метод объявлял обязательный параметр `int $productId`, но роутер (`Core\App::run()`)
подставляет в контроллер только объект `Request`, если он указан в маршруте — параметры
из GET-строки он не читает. Маршрут `/remove-from-cart` зарегистрирован без Request-класса,
поэтому вызов всегда шёл без аргументов и падал с `ArgumentCountError`.
**Стало:** параметр убран, `productId` читается напрямую из `$_GET['product_id']`
(именно оттуда его передаёт ссылка в `cart.php`: `/remove-from-cart?product_id=...`).

### 4. Нерабочая валидация корзины — `Request/CartRequest.php`
**Было:**
- `getProductId()` читал ключ `productId` (camelCase), а форма в `cart.php` отправляет
  поле `product_id` (snake_case) — ключи никогда не совпадали.
- `CartValidate()` в начале стирал все данные (`$this->data = []`), а затем сравнивал
  весь массив `$this->data` с числом `0` — в PHP это всегда даёт `false`, поэтому ни одна
  ошибка никогда не добавлялась. Валидация была полностью нерабочей "заглушкой".

**Стало:** ключ исправлен на `product_id`; `CartValidate()` переписан на реальную проверку
`getProductId()` и `getAmount()` с понятными сообщениями об ошибках.

### 5. Форма изменения количества в корзине шла не туда — `Views/cart.php`
**Было:** форма изменения количества товара отправляла запрос на `/add-product`. Этот
маршрут обрабатывает `ProductController::product()`, где для уже существующего товара
количество **всегда** увеличивалось на 1 — введённое пользователем число в поле `amount`
никак не использовалось.
**Стало:** `action` формы изменён на `/update-cart` — маршрут, который ведёт в
`CartController::updateCart()` и реально устанавливает количество, введённое пользователем
(а не просто прибавляет единицу).

### 6. Проигнорированный результат валидации в `updateCart()` — `Controller/CartController.php`
**Было:** `$request->CartValidate();` вызывался, но результат никуда не сохранялся —
даже при ошибке (например, `product_id <= 0`) код продолжал обновлять корзину.
**Стало:** результат сохраняется в `$errors`; при непустом массиве ошибок — редирект
обратно в корзину без изменений.

### 7. Перевёрнутая проверка авторизации на форме добавления товара — `Controller/ProductController.php`
**Метод:** `getProducts()`
**Было:** `if ($this->authService->check()) { header('Location: /login'); ... }` — форму
добавления товара (`add_product_form.php`) видели именно гости, а залогиненных
пользователей (для которых форма и предназначена) отправляло на логин.
**Стало:** условие исправлено на `if (!$this->authService->check())`.

### 8. Игнорируемое количество товара — `Controller/ProductController.php`
**Метод:** `product()`
**Было:**
- Результат `$request->validateProduct()` никогда не проверялся — невалидные
  `product_id`/`amount` не блокировали выполнение.
- Была объявлена переменная `$amount = 1` с комментарием "всегда добавляем одну единицу",
  но нигде не использовалась. Для новой записи в БД шло `$request->getAmount()`, а для
  уже существующей — жёстко `+ 1`, независимо от того, что ввёл пользователь.

**Стало:** ошибки валидации теперь проверяются (при наличии — редирект в каталог без
изменений); количество во всех случаях берётся из `$request->getAmount()`.

### 9. Утечка чужой корзины гостям — `Controller/ProductController.php`
**Метод:** `catalog()`
**Было:** `$user = $this->authService->getCurrentUser() ?? 1;` — если сессии нет,
`$user` становился числом `1` (как будто это ID пользователя), а не `null`. Дальше стояла
проверка `if (!$user)`, но число `1` в PHP всегда `true`, поэтому эта ветка никогда не
выполнялась — и любому анонимному посетителю каталога подставлялась корзина **реального
пользователя с id = 1**.
**Стало:** для гостя (когда `getCurrentUser()` вернул `null`) корзина явно берётся пустой,
поэтому у всех товаров в каталоге для гостя `amount = 0`, как и должно быть.

### 10. Автовход после регистрации вёл не туда — `Controller/UserController.php`
**Метод:** `registrate()`
**Было:** после успешного `$this->authService->auth(...)` (реально создаёт сессию —
пользователь становится залогинен) код всё равно редиректил на `/login`. А `getLogin()`
не проверяет, что пользователь уже вошёл, и просто показывает форму логина заново —
получалось, что после регистрации человек видел форму входа, будто ничего не произошло.
**Стало:** редирект изменён на `/catalog`, как и при обычном успешном входе через `login()`.

### 11. Редирект на несуществующий маршрут — `Controller/UserController.php`
**Метод:** `updateProfile()`
**Было:** при ошибках валидации — `header('Location: /profile/edit');`, а такого
маршрута в приложении нет (в `Core\App` зарегистрирован `/profile-change`). Пользователь
получал бы 404 вместо формы со своими ошибками.
**Стало:** редирект исправлен на `/profile-change`.

### 12. Ложная ошибка "email уже существует" — `Request/ProfileRequest.php`
**Метод:** `validateProfileUpdate()`
**Было:** метод искал в БД пользователя с указанным email и, если находил кого-либо,
сразу писал ошибку — но находил в том числе **самого текущего пользователя**. Если
человек менял только имя, оставляя email прежним, форма всё равно ложно говорила
"Этот Email уже существует".
**Стало:** метод принимает `currentUserId` (передаётся из `UserController::updateProfile()`);
ошибка ставится, только если найденный пользователь с таким email — это кто-то другой,
а не сам текущий пользователь.

### 13. Исключение вместо понятного сообщения при оформлении заказа — `Controller/OrderController.php`
**Метод:** `handleCheckout()`
**Было:** проверка минимальной суммы заказа (`$sum < 1000`) бросала исключение **вне**
блока `try/catch` (тот `try/catch` относится только к созданию заказа). Исключение
долетало до общего обработчика в `Core\App::run()`, который на любой `Throwable`
показывает страницу `500.php` — пользователь видел "ошибку сервера" вместо понятного
сообщения на форме заказа.
**Стало:** вместо `throw` — возврат той же формы заказа (`order_form.php`) с
сообщением в `$errorMessage`.

### 14. Сообщение об ошибке нигде не выводилось — `Views/order_form.php`
**Было:** контроллер уже давно клал текст ошибки в переменную `$errorMessage`
(например, при сбое создания заказа в `OrderService`), но шаблон формы никогда её не
выводил — пользователь видел пустую форму заново без объяснений.
**Стало:** добавлен вывод `$errorMessage` красным текстом над формой, если оно есть.

## Что не трогали (замечено, но не является активным багом)

- В `src1/public/index.php` маршрут `/add-product` (POST) регистрируется дважды: сначала
  на несуществующий метод `CartController::addProductToCart`, затем на
  `ProductController::product`. Так как побеждает последняя регистрация, первая строка
  сейчас мёртвый код и ни на что не влияет — но если порядок строк поменять, приложение
  упадёт с ошибкой "метод не найден". Стоит либо удалить лишнюю строку, либо реализовать
  метод `addProductToCart`.
- `Model/Order_products::getByAllOrderId()` содержит синтаксически неверный SQL
  (`WHERE order_id = :$orderId` при биндинге `orderId`), но метод нигде не вызывается —
  оставлен как есть, чтобы не менять код, который не влияет на работу приложения.
- `Service/Auth/AuthCookieService` — рабочая, но неиспользуемая альтернативная реализация
  авторизации через cookie (везде используется `AuthSessionService`). Оставлена как есть.

## Проверка

Все изменённые PHP-файлы проверены на синтаксис (`php -l`) — ошибок не найдено.
Функционального тестового окружения (composer/PHPUnit) в проекте нет, поэтому изменения
не покрыты автотестами — рекомендуется прогнать сценарии вручную:
регистрация → автовход → каталог → корзина (добавление/изменение количества/удаление) →
оформление заказа (в т.ч. с суммой < 1000) → редактирование профиля (в т.ч. без изменения
email).
